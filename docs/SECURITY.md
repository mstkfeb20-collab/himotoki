# セキュリティとエラー処理

himotoki は**ソースコード・設計書・DB 定義を読み、それをAPIで返すサーバ**です。守るべきものは、サーバ上のファイルの中身と、環境変数にある資格情報（DB・Git・LLM のトークン）です。本書は想定する脅威、実装済みの対策、導入時の設定、残っているリスクをまとめます。

## 1. 想定する脅威

| # | 攻撃者・経路 | 例 |
|---|---|---|
| T1 | HTTP ポートに到達できる人 | API で任意のファイルを読む、任意のディレクトリをインデックスさせる、任意のホストの DB に接続させる |
| T2 | 利用者のブラウザで開かれた悪意あるページ | ローカルで動くビュワー（127.0.0.1:8765）に対する CSRF・DNS リバインディング・クロスサイト WebSocket |
| T3 | 偽の Webhook | 署名の無い push / MR イベントで fetch・インデックスを走らせる、ブランチ名に git のオプションを仕込む |
| T4 | 細工されたリポジトリ・設計書 | リポジトリ外を指すシンボリックリンク、巨大ファイル、XML の実体参照（XXE・billion laughs）、zip 爆弾の xlsx/docx |
| T5 | エラー応答・ログ経由の漏えい | スタックトレース、DSN に含まれるパスワード |
| T6 | 依存ライブラリの既知の脆弱性 | |

## 2. 実装済みの対策

### 2.1 API とビュワー（T1・T2）

| 対策 | 内容 | 設定 |
|---|---|---|
| トークン認証 | `HIMOTOKI_API_TOKEN` を設定すると、`/api/*` と WebSocket に `Authorization: Bearer` またはクッキーを要求する。ビュワーは `?token=` 付き URL で一度開くと、HttpOnly・SameSite=Strict のクッキーに保存し、URL からトークンを消す | `HIMOTOKI_API_TOKEN` |
| ネットワーク公開の拒否 | `serve --host` がローカル以外のときは、トークンと許可ホスト名が無ければ起動しない | `HIMOTOKI_ALLOW_NO_AUTH=1`（認証付きプロキシの裏に置く場合のみ） |
| Host ヘッダの検査 | 許可したホスト名以外は 400。DNS リバインディング対策 | `HIMOTOKI_ALLOWED_HOSTS`（既定: localhost, 127.0.0.1, ::1） |
| CORS | 既定では無効（同一オリジンのみ）。以前の全オリジン許可は廃止 | `HIMOTOKI_CORS_ORIGINS`（必要なときだけ列挙） |
| クロスサイト WebSocket の拒否 | Origin がホストと一致しない接続は閉じる（ブラウザは WebSocket に CORS を適用しないため） | |
| ファイル読み取りの制限 | コード表示はリポジトリ／設計書フォルダの中だけ（`../`・絶対パス・外を指すシンボリックリンクは拒否）。設計書の取込確認（`/api/docs/check`）は、グラフに設計書として登録されたファイルだけを読み直す（任意のファイル名は 404）。Office ファイルは展開前に zip 爆弾を検査し、内部の XML は defusedxml で読む | |
| 入力パスの制限 | API で指定するリポジトリ（システム単位の `repos` の各パスを含む）・設計書フォルダ・辞書 CSV・実行時 SQL CSV は許可ルート配下のみ。グラフ名・ソース名は英数字と `._-@` のみ。システム単位のリポジトリ名はグラフ内のパスの先頭になるため英数字と `._-` のみ（`/`・`..`・`design` は拒否）、コード表示はその名前に対応するリポジトリの中だけを読む | `HIMOTOKI_ALLOWED_ROOTS`（コンテナでは `/repos:/data`） |
| API からの DB 接続は明示的に許可 | DSN を受け取る取込 API は既定で 403（任意ホストへの接続を防ぐ）。CLI と CSV 取込は従来どおり | `HIMOTOKI_ALLOW_DB_FROM_API=1` |
| 入力サイズ | 要求文・指示・コメントは 10 万字、探索の深さは 1〜8、一括判断は 5 万件まで | |
| レスポンスヘッダ | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`。ビュワーには CSP（スクリプトは自オリジンのみ） | |

### 2.2 Webhook と git（T3）

- `HIMOTOKI_WEBHOOK_SECRET` が未設定なら Webhook は 503 で拒否します（以前は未設定だと無認証で受け付けていました）。
- 検証は GitLab のトークン、または GitHub の HMAC-SHA256 署名で行い、比較は定数時間です。本文は 5 MB まで受け付けます。
- イベント中のブランチ名・SHA は形式を検査し、`-` で始まるもの、`..` を含むもの、空白・記号を含むものは拒否します（git のオプションとして解釈させないため）。
- git の呼び出しは引数リスト（シェルを介さない）で行います。タイムアウト付き（`HIMOTOKI_GIT_TIMEOUT`、既定 900 秒）で、資格情報の入力待ちで止まらないよう `GIT_TERMINAL_PROMPT=0` にしています。
- 処理は別スレッドで行い、結果（成功・失敗とその理由）は `GET /api/hooks/log` で確認できます。

### 2.3 リポジトリ・設計書の取り込み（T4）

| 対策 | 内容 |
|---|---|
| シンボリックリンク・サブモジュール | 追わない（git のモード 120000 / 160000 を除外し、実パスがリポジトリ内かも確認） |
| ファイルサイズ | 上限を超えるファイルは読み込まずにスキップし、取込状況のエラーとして報告する（`HIMOTOKI_MAX_FILE_MB`、既定 8 MB。設計書は 4 倍） |
| XML | 実体宣言を含む XML は処理しない（XXE・billion laughs 対策）。外部実体は取得しない。expat 2.6 |
| Office | 展開前に zip の総展開サイズ・エントリ数・圧縮率を検査する（`HIMOTOKI_MAX_OFFICE_MB`、既定 200 MB） |
| 外部コマンド | psql は `--dbname=` で DSN を渡す（`-` で始まる DSN をオプションとして解釈させない）。LibreOffice の変換・psql・git はすべてタイムアウト付き |
| YAML | ルールパックは `yaml.safe_load` |

### 2.4 漏えい防止（T5）

- 想定外の例外は、サーバログにスタックトレースを残し、クライアントには `internal error` と参照 ID だけを返します。
- 解析の失敗をビュワーに送るイベントからスタックトレースを外しました（以前はトレースを送っていました）。
- psql の失敗時は、コマンドライン（DSN とパスワードを含む）を例外に載せず、標準エラーを伏せ字処理してから返します。インデックス・取込・Webhook のエラーメッセージも同じ処理を通します（`password=`・`token=`・URL 中の `user:pass@` を `***` に置換）。

### 2.5 依存関係（T6）

| 対象 | ツール | 結果 |
|---|---|---|
| Python（requirements.txt） | pip-audit | 既知の脆弱性なし |

フロントエンドでは、開発サーバの Vite / esbuild に「任意の Web サイトが開発サーバの応答を読める」脆弱性（GHSA-67mh-4wv8-2f99）があったため、Vite 7 に更新しました。

### 2.6 コンテナ

- 一般ユーザー（uid 10001）で実行します。
- 公開ポートは既定で 127.0.0.1 に限定しています（Neo4j も同様）。
- `HIMOTOKI_API_TOKEN` と `NEO4J_PASSWORD` が未設定だと起動しません。

## 3. 導入時のチェックリスト

1. `HIMOTOKI_API_TOKEN` に十分長いランダム値を設定する（`python -c "import secrets; print(secrets.token_urlsafe(32))"`）。
2. 利用者がアクセスするホスト名を `HIMOTOKI_ALLOWED_HOSTS` に設定する。
3. 社内ネットワークに公開する場合は、TLS を終端するリバースプロキシの裏に置く（本体は TLS を持たない）。
4. `HIMOTOKI_ALLOWED_ROOTS` を、解析してよいリポジトリ・設計書の置き場所に限定する。
5. Webhook を使うなら `HIMOTOKI_WEBHOOK_SECRET` を設定し、GitLab / GitHub 側にも同じ値を登録する。コメント投稿用のトークンは、対象プロジェクトだけに書き込める最小権限にする。
6. DB 辞書は、可能なら CSV エクスポートで渡す。直接つなぐ場合は、辞書ビューの参照権限だけを持つ読み取り専用ユーザーを使う。
7. `ANTHROPIC_API_KEY` を設定すると、要求文とコード断片が判定のため Anthropic の API に送られる。社内の情報持ち出し基準に照らして判断する（未設定ならすべてローカルで動く）。

## 4. 残っているリスク・未対応

| 項目 | 内容 | 方針 |
|---|---|---|
| 利用者単位の権限 | トークンは 1 つで全員同じ権限。判断の「誰が」は自己申告の名前 | SSO（OIDC）対応の認証プロキシの利用を推奨。将来はユーザー・ロールと監査ログを本体に持たせる |
| レート制限 | API にリクエスト数の制限は無い（同時接続数の上限のみ。`HIMOTOKI_MAX_CONNECTIONS`） | プロキシ側で制限する |
| TLS | 本体は HTTP のみ | プロキシで終端する |
| プロンプトインジェクション | Claude 判定時、リポジトリや設計書の文章がプロンプトに入る。悪意ある文章で判定が歪む可能性がある | 判定はツール実行を伴わず、影響は判定結果に限られる。最終判断は人の承認を前提とする |
| ルールパック | 正規表現・テンプレートを含む設定で、信頼された管理者が書く前提（極端な正規表現で処理が遅くなりうる） | ルールパックはコードと同様にレビューして配置する |
| LibreOffice | `.xls` / `.doc` の変換で外部ソフトに未信頼の文書を渡す | 必要なときだけ導入する。マクロは実行されない既定設定で使う |
| MCP サーバ | stdio で起動したローカル利用者を信頼する（認証なし） | ネットワーク越しに公開しない |
| 実機未検証 | Neo4j 接続・TLS 構成・プロキシ構成は、作成環境で動かせていない | 導入時に確認する |

## 5. エラー処理の方針

| 場面 | 振る舞い |
|---|---|
| 1 ファイルの抽出失敗（壊れたファイル、文字コード、上限超え、実体宣言付き XML） | そのファイルだけをスキップし、インデックスは続行する。取込状況の「抽出エラー」に件数と例を出す |
| インデックス全体の失敗 | 状態を `error` にし、伏せ字処理したメッセージを `/api/index` で返す。直前のグラフはそのまま残る（グラフの差し替えは成功時のみ） |
| 解析（Run）の失敗 | Run を `error` にしてメッセージをビュワーに通知する。トレースはサーバログのみ |
| 横断検索の失敗（検索サーバ停止など） | その工程だけ失敗として記録し、ほかの工程は続ける |
| Claude API の失敗・タイムアウト | 90 秒で打ち切り、2 回まで再試行し、それでも失敗したらルールベースの判定に切り替える（`HIMOTOKI_LLM_TIMEOUT`） |
| Webhook の処理失敗 | `GET /api/hooks/log` に失敗と理由を残す（送信元には受付時点で応答済み） |
| 同じグラフの同時インデックス | グラフごとの排他で順番に実行する。API からの二重起動は 409 |
| 保存ファイルの破損 | workspace.json・ソース・グラフは一時ファイルに書いてから置き換えるため、書き込み途中の破損は起きない。読めない workspace.json は退避して空から始める。抽出キャッシュ（facts.db）は破損時に退避して作り直す（再抽出で復旧） |
| 外部コマンドのハング | git・psql・LibreOffice はタイムアウトで打ち切る |

## 6. 検証

`backend/tests/test_security.py` では、上記の攻撃を 1 件ずつ試して、失敗することを確認しています。

- `../` や絶対パスによるファイル読み取り
- 他オリジンからの CORS、Host ヘッダの偽装、クロスサイト WebSocket
- トークン無しでのアクセスと、トークン入りクッキーの属性
- 許可ルート外のパスの指定、名前によるディレクトリトラバーサル
- API からの DB 接続
- Webhook のシークレット未設定・不正な署名・オプションを仕込んだブランチ名
- 入力サイズの上限
- シンボリックリンク経由の秘密ファイルの読み込み、上限を超えるファイル
- XXE・billion laughs・zip 爆弾

あわせて、実際のサーバとブラウザ（Chromium）でも次の点を確認しました。

- 修正前に再現した `/etc/passwd` の読み取りが 404 になること
- トークンでログインしたあともビュワーとリアルタイム更新が CSP の下で動くこと
