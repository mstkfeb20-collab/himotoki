# 取り込みの再現率（関係単位）

影響分析の前提として、グラフが「資産のあいだの実在する関係」をどれだけ持っているかを測る。

## 題材

`sor-bench-r.bundle`：販売在庫管理システム（HZK、264 ファイル）。himotoki のコードを見ていない別エージェントが、
「SoR あるある」を想定してゼロから作ったもの。Struts 1 / Spring MVC / MyBatis / iBATIS / JDBC、Oracle DDL・PL/SQL、
ksh（共通関数経由の起動・送受信）、JP1/AJS3、SQL*Loader、レイアウト定義（固定長・CSV・COBOL コピー句）、帳票 XML、
設計書（Markdown・CSV・xlsx）。Shift_JIS 混在、命名の揺れ、死んだファイル、層ごとに桁が違う潜在バグを含む。

正解は `_truth/relations.jsonl`（4,063 件・30 種類）。題材と同じ仕様から生成されたもので、himotoki の出力からは作っていない。
**測定のときは `_truth/` を除いたコピーを取り込む。**

## 測り方

```
git clone sor-bench-r.bundle bench && cp -r bench bench-src && rm -rf bench-src/_truth
python score.py bench-src bench/_truth/relations.jsonl --out result.json [--backend <測る版の backend>]
```

* 資産 → ノード：要素名（クラス・メソッド・テーブル・列・ジョブ・アクション・フォーム項目・検証・レイアウト項目・帳票項目・設定・メッセージ・連携ファイル）で引き、
  見つからない・要素名が無いときはそのファイルのノード全体。メソッドはその中の SQL 文を含む。
* **直接**：2 つの資産のあいだに辺がある（向き・種類は問わない）。
* **近く**：3 ステップ以内でつながる（辺が 60 本以上のハブは通らない）。
* **対応なし**：どちらかの資産がグラフに無い（読み取りの漏れ）。
* `length_fact` は、さらに「その場所の桁の値がグラフに記録されているか」を数える。

## 結果（2026-11-12）

|---|---:|---:|---:|
| 追加前（ede4b05） | 55.5% | 63.8% | 1,161 件 |
| 追加後（ad6c1c7） | **81.0%** | **94.1%** | 2 件 |

桁の値が記録されている割合（length_fact 933 件）：0% → 90%。

## まだ取れていないもの（この題材を見たあとに直すと題材への合わせ込みになるため、直すなら別の新しい題材で測り直す）

* フォーム項目 → 列（78 件、直接 0%）：画面の項目がどの列に入るかは、Java の代入と SQL のバインドを通るデータの流れで、グラフに辺が無い。
* シェルの共通関数経由の SQL 実行（`run_sql xxx`、7 件中 1 件）・別クラスの定数で組み立てる出力ファイル名。
* ビューの列（`V_URIAGE_SUMMARY.CUST_CD`）・SQL*Loader の列単位の書き込み。
* XML のコメントに書かれた ID、xlsx の画面項目定義書のうち ID が表の外にある行。
* Spring 側フォーム（注釈で桁を書くもの）の桁。

## 注意

* 要素名で引けずファイル単位に広げた端点がある（要素名つきの端点の 1 割弱）。その分、直接・近くは甘めに出る。
* 「近く」はつながっていることを示すだけで、意味のある経路かは問わない。
