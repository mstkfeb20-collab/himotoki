# 自作の SoR 題材（sor-bench）

公開リポジトリには、SoR の改修で漏れやすいもの（ジョブ定義、運用シェル、DB にだけある定義、連携ファイルのレイアウト、帳票定義、Excel / Word の設計書）がほとんど含まれていません。そこで、架空の販売管理システムと改修依頼 8 件を作り、比較に使います。

## 作り方（評価との切り離し）

- 題材は、この評価の会話の文脈を持たない別のエージェントが作りました。作り手には himotoki のリポジトリを読むことを禁じ、ツールの存在にも触れていません。渡した指示は下に全文を載せています。
- 指示の要点は「10 年選手の業務システムの普通の作り（つながりが追いにくい作りも現実にありがちな割合で含め、わざと極端にはしない）」と「各改修は、設計書まで含めて漏れなく正しく直す」です。
- 正解は、各改修ブランチのコミットで実際に変更・削除されたファイルです（テストコードと新規ファイルは除く）。`tasks_sor.json` は、作り手が出力した一覧から機械的に作りました。
- 題材を受け取ったあと、題材にも himotoki のルール・コードにも、この題材に合わせた変更はしていません。

## 題材の中身

- `sor-bench.bundle`（git bundle）。`main` が改修前の状態（140 ファイル）、`cr/01`〜`cr/08` が各改修（どれも main から分岐した 1 コミット）
- フォルダ: `ap-server/`（Struts1 風の Java・JSP・MyBatis・メッセージ）、`batch-server/`（Java バッチ・シェル・SQL*Plus・JP1 定義・crontab・連携レイアウト・帳票定義）、`db-server/`（Oracle の DDL・ビュー・トリガー・PL/SQL・DB リンク）、`if-server/`（ファイル送受信）、`docs/`（Excel / Word の設計書）

| 課題 | 正解のファイル数 | 依頼の要旨 |
|---|---|---|
| cr01 | 4 | 受注一覧の最大表示件数を 500 件から 1000 件に |
| cr02 | 6 | 20 日締めを追加し、月末締めと同じ流れで会計連携まで |
| cr03 | 19 | 受注入力に「客先注文番号」を追加し、出荷指示データと請求書の明細にも出す |
| cr04 | 25 | 得意先コード（TOKUI_CD）を 6 桁から 8 桁に（物理名入りの依頼） |
| cr05 | 12 | 受注側の消費税の端数処理を、得意先マスタの端数処理区分に従わせる |
| cr06 | 11 | 受注区分に「直送」を追加（在庫引当・出荷指示はせず、登録時点で出荷済） |
| cr07 | 10 | 入金データに振込手数料が追加。消込・請求残は「入金額＋手数料」で |
| cr08 | 3 | 請求書の明細に納品日を印字 |

## システムの題材
架空の「販売管理システム」（受注・出荷・請求）。社内で1つの git リポジトリ（モノレポ）にまとめられている想定で、サーバ単位でフォルダを分けてください。目安として 80〜150 ファイル。

含めてほしい「SoRあるある」（全部でなくてよいが、多くを自然に含める）:
- Java（古めのスタイル）: Servlet/Struts風のActionやService、DAO。JDBC直書き（PreparedStatementとSQL文字列）、StringBuilderで組み立てる動的SQL、定数クラス、区分値の定数やマジックナンバー、似たロジックのコピペ（複数箇所に同じ計算）、共通Util、日本語コメント
- 一部は MyBatis 風の XML マッパー（resultMap、SQL断片の include など）
- Oracle の DDL（テーブル、ビュー、シーケンス、トリガー）、PL/SQL パッケージ（締め処理など）、列名はローマ字略称（例: JUCHU_NO, TOKUI_CD, SURYO, KINGAKU, ZEI_KBN）、別システムへの DB リンク参照が1〜2箇所
- 画面: JSP（入力・確認・一覧）、入力チェック（JS や Java 側）、メッセージは properties（日本語メッセージ）
- バッチ: Java のメインクラス、それを呼ぶシェルスクリプト（環境変数・引数・SQL*Plus呼び出し・ファイル転送 sftp/cp）、JP1 のジョブネット定義（ajsprint 風のテキスト）や crontab
- 外部連携: 固定長・CSV の連携ファイル（出荷指示ファイル、請求データなど）を出力／取込するプログラムと、そのレイアウト定義
- 帳票（請求書など）の出力処理（帳票定義はXMLやCSVレイアウト、あるいは Java で直接組み立て）
- 設計書: docs/ 以下に Excel（.xlsx）と Word（.docx）で。テーブル定義書（シートごとに表）、画面項目定義書、連携ファイルレイアウト定義書、CRUD表、基本設計書（Word）。書式は現場風に（表の上にタイトルや改訂履歴、列見出しは「項目名」「物理名」「型」「桁数」「備考」など現場で普通の言い方。見出しの言い方は資料ごとに多少揺れていてよい）。Python の openpyxl / python-docx で作って構いません
- テスト: JUnit が少しだけある（全部には無い）
- 古いコメントアウトや使われていないクラスが少し残っている

## 改修案件（8件）
上のシステムに対する、現場で典型的な改修依頼を8件作ってください。例（そのまま使わなくてよい）: 項目の桁拡張、区分値の追加、新項目の追加（画面→DB→帳票→連携ファイルまで波及）、税計算・端数処理の変更、締め処理の条件変更、連携ファイルのレイアウト変更、帳票の項目追加、項目の廃止。
- 規模は小（2〜3ファイル）から大（10ファイル以上）まで混ぜる
- 依頼文は、業務部門や上流SEが書く日本語のチケットのように書く（1〜3文。画面名・帳票名・業務用語は使ってよいが、ファイル名・クラス名・物理名は原則書かない。現場でたまにあるように、1件か2件は物理名を書いてもよい）
- 各案件は、実際に必要な修正をすべて正しく行ってください（コード、SQL、DDL、画面、メッセージ、連携レイアウト、帳票、ジョブ、そして設計書の該当箇所も更新する。テストがあるものはテストも）。漏れなく直すのが正解データになります

## 実行手順

```bash
cd eval/agent_compare
git clone sor-bench.bundle ~/work/sor-bench
python prepare.py --tasks tasks_sor.json --repo ~/work/sor-bench --out ~/compare-sor --prompt prompt_sor.txt
ALLOW_PYTHON=1 MODEL=opus BUDGET=10 ./run.sh ~/compare-sor
python score.py --tasks tasks_sor.json --out ~/compare-sor
```

`ALLOW_PYTHON=1` は、両方の条件に python の実行を許します。設計書は Excel / Word なので、単体の条件でもエージェントが python（openpyxl など）で読めるようにするためです（現場の Claude Code でも普通に使える手段なので、許さないと himotoki 側に有利になります）。
