# 自作の SoR 題材・大規模版（sor-bench-l）

[sor-bench](SOR_BENCH.md)（140 ファイル）では、エージェント単体でも正解を全部見つけられ、himotoki の出番がほとんどありませんでした。grep の結果があふれ、エージェントが全体を見渡せない規模での差を見るため、大規模版を作りました。

## 作り方（評価との切り離し）

- 前回と同じく、この評価の会話の文脈を持たない別のエージェントが作りました。作り手には himotoki のリポジトリと前回の題材を読むことを禁じ、ツールの存在にも触れていません。指示の全文は下に載せています。
- 正解は、各改修ブランチのコミットで実際に変更・削除されたファイルです（テストコードと新規ファイルは除く）。`tasks_sor_l.json` は、作り手が出力した一覧から機械的に作りました。作り手には、変更したファイルごとに理由も書かせています（リポジトリ外の `BENCH_TASKS.json`）。
- 題材を受け取ったあと、題材にも himotoki のルール・コードにも、この題材に合わせた変更はしていません。

- 特定の解析ツールで解析しやすいように作る必要はありません。実際の現場で見かける「つながりが追いにくい」作りも、現実にありがちな割合で含めてください。逆に、わざと極端に難しくする必要もありません。普通の、15年選手の大規模業務システムの雰囲気を目指してください。
- ネットワークには出られない前提で、手元の Python（openpyxl / python-docx あり）、Java（javac あり）、git だけで作ってください。

## システムの題材
架空の中堅卸売業の「基幹システム」。社内で1つの git リポジトリ（モノレポ）にまとめられている想定です。目安として **1,000〜1,500 ファイル**。

規模のある業務システムらしく、複数のサブシステムに分かれ、DB を共有しつつ、サブシステム間はファイル連携・DB リンク・共通テーブルでつながっている構成にしてください。例:
- 販売管理（見積・受注・出荷・売上・請求・入金）
- 購買管理（発注・入荷・仕入・支払）
- 在庫・物流（在庫引当・倉庫間移動・棚卸・倉庫管理システムとの連携）
- 会計連携（仕訳データ作成・会計パッケージへの送信、月次・年次締め）
- マスタ管理（得意先・仕入先・商品・単価・倉庫・社員・カレンダー・区分マスタ）
- 共通基盤（共通部品、採番、ログ、日付・税計算・端数処理のユーティリティ、帳票基盤、ジョブ共通シェル）
- 外部 EDI（取引先との受発注データ交換）

大規模であることが重要です。同じ業務用語・同じ列名（例: 得意先コード、商品コード、数量、金額、税区分）が多くのサブシステム・多くのファイルに出てきて、grep すると大量にヒットする状態が自然に生まれるようにしてください（現実の大規模システムがそうであるように）。一方で、今回の改修で直す必要がないファイルも当然たくさんあります。

量産部分（似た構造の画面・DAO・バッチ・テーブル定義が多数並ぶ部分）は、現場と同じく「テンプレートからの量産」で構いません。スクリプトで生成してよいですが、現場同様に、作られた時期や担当者によって書き方が揺れる（命名、共通部品を使う／使わない、コピペして少し変えた処理、古い書き方の残骸）ようにしてください。中核の業務ロジック（税計算、締め、引当、消込、仕訳生成など）は手で書いたような中身にしてください。

含めてほしい「SoRあるある」（全部でなくてよいが、多くを自然に含める）:
- Java（古めのスタイル）: Servlet/Struts風のActionやService、DAO。JDBC直書き（PreparedStatementとSQL文字列）、StringBuilderで組み立てる動的SQL、定数クラス、区分値の定数やマジックナンバー、似たロジックのコピペ（複数箇所に同じ計算）、共通Util、日本語コメント。サブシステムごとに少しずつ流儀が違う
- 一部は MyBatis 風の XML マッパー（resultMap、SQL断片の include など）
- Oracle の DDL（テーブル、ビュー、シーケンス、トリガー、シノニム）、PL/SQL パッケージ（締め処理・集計など）、列名はローマ字略称（例: JUCHU_NO, TOKUI_CD, SURYO, KINGAKU, ZEI_KBN）、別システムへの DB リンク参照
- 画面: JSP（入力・確認・一覧・照会）、入力チェック（JS や Java 側）、メッセージは properties（日本語メッセージ、メッセージIDで参照）
- バッチ: Java のメインクラス、それを呼ぶシェルスクリプト（共通の環境設定シェルを読み込む、引数、SQL*Plus 呼び出し、SQL*Loader の ctl、ファイル転送 sftp/cp）、JP1 のジョブネット定義（ajsprint 風のテキスト）や crontab
- 外部連携: 固定長・CSV の連携ファイルを出力／取込するプログラムと、そのレイアウト定義（形式はサブシステムごとに揺れていてよい）
- 帳票（請求書・納品書・発注書・各種一覧表など）の出力処理と帳票定義
- 設定ファイル（properties・XML）、区分値マスタの初期データ（INSERT 文や CSV）
- 設計書: docs/ 以下に Excel（.xlsx）と Word（.docx）で、サブシステムごとに。テーブル定義書、画面項目定義書、連携ファイルレイアウト定義書、CRUD表、帳票レイアウト定義、バッチ処理定義、基本設計書（Word）など。書式は現場風に（表の上にタイトルや改訂履歴、列見出しの言い方は資料ごとに揺れていてよい）。全部の部品に設計書があるわけではなく、古いものは更新されていないものもある、というのも現実的です
- テスト: JUnit が少しだけある（全部には無い）
- 古いコメントアウトや使われていないクラス、旧版のファイル（_old や日付付きのバックアップ）が少し残っている

## 改修案件（12件）
上のシステムに対する、現場で典型的な改修依頼を12件作ってください。例（そのまま使わなくてよい）: 項目の桁拡張、区分値の追加、新項目の追加（画面→DB→帳票→連携ファイルまで波及）、税計算・端数処理の変更、締め処理の条件変更、連携ファイルのレイアウト変更、帳票の項目追加、項目の廃止、取引先追加に伴う EDI 対応、マスタ項目の追加、サブシステムをまたぐ改修。
- 規模は小（2〜3ファイル）から大（30ファイル以上）まで混ぜる。半分程度は複数のサブシステムにまたがるもの
- 依頼文は、業務部門や上流SEが書く日本語のチケットのように書く（1〜3文。画面名・帳票名・業務用語は使ってよいが、ファイル名・クラス名・物理名は原則書かない。現場でたまにあるように、1〜2件は物理名を書いてもよい）
- 各案件は、実際に必要な修正をすべて正しく行ってください（コード、SQL、DDL、画面、メッセージ、連携レイアウト、帳票、ジョブ、設定、そして設計書の該当箇所も更新する。テストがあるものはテストも）。漏れなく直すのが正解データになります。量産部分に影響する改修でも、影響する全ファイルを直してください（変更はスクリプトで入れて構いませんが、その案件に必要な箇所だけを変えること）
- 直す必要のないファイルは変えないでください（整形の変更や、ついでの修正もしない）

## git の作り方
1. リポジトリを git init し、ベースのシステム一式を1コミット（メッセージ "baseline"、ブランチ main）
2. 各案件について、main（baseline）から枝分かれしたブランチ `cr/01`〜`cr/12` を作り、その案件の修正だけを1コミットで入れる（コミットメッセージ＝依頼文そのもの）。案件同士は独立（どれも baseline から分岐）
3. git の user は "bench <bench@example.com>" を使う
