# himotoki の作業指示で開発する

issue（本文に `himotoki-run: <run ID>` の印があるもの）か run ID から、himotoki の作業指示（MCP の `get_handoff`）を取り、その範囲で実装して、最後に予測と実際の変更を突き合わせます（`verify_change`）。

## 前提

- himotoki の MCP サーバが登録されていること（`get_handoff`・`verify_change`・`get_element` が見える）。無ければ登録方法（ビュワーの「開発へ渡す」→「Claude Code で実装」）を案内して止まる。
- 実装するリポジトリの中にいて、作業ツリーがきれいなこと（`git status --porcelain` が空）。未コミットの変更があれば、どうするか聞く。

## 手順

1. **作業指示を引く。**
   - 引数が issue 番号・URL なら `gh issue view <番号> --json number,title,body,url` で本文を読み、`himotoki-run: (\w+)` から run ID を取る。印が無ければ run ID を聞く。
   - 引数が run ID ならそのまま使う。
   - `get_handoff(run_id)` を呼ぶ。`warnings`（未承認・未判定）があれば最初に伝える。
2. **計画を見せる。** 修正対象のファイルと理由、除外（触らないもの）、未判定、トランザクション・連携の注意、関連する設計書、実行するテストを短くまとめ、進めてよいか聞く。issue がサブシステム単位（タイトルが「… — <フォルダ>」）なら、そのフォルダの対象だけを今回の範囲とする。
3. **ブランチを切る。** 既定ブランチから `himotoki/<run ID>-<issue 番号>`（issue が無ければ `himotoki/<run ID>`）を作る。作業前のコミット（base）を控える。
4. **実装する。** `rules_for_agent` に従う。要点:
   - 修正対象の範囲で直す。範囲外のファイルを直す必要が出たら、理由を書いて止まり、確認を求める（勝手に広げない）。
   - 除外された要素は変更しない。
   - 未判定の要素は、中を読んで影響の有無を確かめ、結論を記録する（後で issue に書く）。
   - 中身やつながりが分からない要素は `get_element`・`neighbors` で確かめる。
   - Excel・Word の設計書は、該当箇所（ファイル・シート・行）を一覧にして人に更新を頼む。ユーザーが求めたときだけ python（openpyxl / python-docx）で直す。
5. **テストする。** 作業指示の「実行するテスト」を実行する。ビルド・テストの方法はリポジトリの README やビルド定義から確かめ、分からなければ聞く。テストが無い修正対象には、テストの追加を提案する。
6. **コミットする。** 意味のある単位でコミットし、メッセージに issue 番号（`refs #<番号>`）を入れる。
7. **予測と突き合わせる。** `verify_change(run_id, base=<控えたコミット>, head=<ブランチ>)` を呼ぶ。himotoki のワークスペースが見ているリポジトリにブランチが無いと照合できないので、エラーになったらブランチを push してから再度試す（push してよいか先に聞く）。
8. **報告する。** 変えたファイル、未判定の結論、予測にあって触らなかった要素とその理由、予測に無かった変更（漏れ）を短くまとめる。issue があれば、同じ内容を `gh issue comment <番号> --body-file` で残してよいか聞いてから書く。PR を作るかどうかも聞く。

## 守ること

- 作業指示の範囲を勝手に広げない。広げる必要が出たら止まって聞く。
- 予測漏れ（`verify_change` の missed）は隠さず報告する。himotoki の学習に使われ、次の影響調査が良くなる。
